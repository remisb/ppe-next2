How this model is kept current

  • One model (model.mjs) generates every diagram on this page and the Structurizr DSL below, so views never drift from each other.
  • Relationships are recorded at the lowest true level (component or container); the context and container views derive implied relationships from them, like Structurizr does.
  • Re-check against these sources on each change: docker-compose.prod.yml (containers, ports, volumes), deploy/Caddyfile (routing), cmd/api/config.go (external endpoints), internal/* (components), web/apps/* (SPAs), docs/architecture/adr and context-map.md.
  • Lives in the repo at docs/architecture/c4/ (instructions: docs/architecture/c4-model.md); reviewed with every ADR.

C4 conventions applied

  • Every diagram has a title naming its type and scope, a short description and a key.
  • Every element shows name, type and technology (containers, components) plus one-sentence responsibility.
  • Every relationship is one-directional with a verb-phrase label and its protocol/technology.
  • External people and systems are grey; the system/container in scope is drawn as a dashed boundary.
  • Shapes carry meaning only beyond colour: cylinder = database, browser window = SPA, folder = file store, dashed border = batch job.

Not modelled (yet)

  • Planned bounded contexts from ADR 0001 (People split, Competence, Projects & crew, Timesheets, Reporting, outbox worker).
  • Build-time systems: GitHub Actions CI and the private remisb/dbbackup module fetched during image builds.
  • The development setup (Vite dev servers on 5180–5188, local Postgres on 5442).
  • Dynamic diagrams (e.g. the order lifecycle: Create → ORDERED → confirmation link → GIVEN).
