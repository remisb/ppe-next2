01

Summary

Status · 7 Oct 2026

Phase 0's code is done: GET /ready, the image healthcheck (/api -healthcheck), the commit in /ready, log rotation on every prod service, and make prod-up waiting for /ready. The uptime check and DigitalOcean alerts are account settings, described in docs/monitoring.md. One correction to 5.1: Docker does not restart an unhealthy container; the healthcheck only reports.

Phase 1 is built (docs/specs/audit-service.md): the Audit log in Administration with filters in its address and a change beside the list; the missing events for users, item sets, employee and item details; request ID, sign-in and app on every change; and the Changes of employees, items and orders in the staff app. A record's list is called Changes, because the glossary keeps "History" for Orders. Its routes are /api/v1/audit-events/{employees|catalogue|orders|users}/{id}. Export, Verify and retention stay in phase 4.

Phase 2 is built (docs/specs/security-service.md, ADR 0003). auth_events records every sign-in, failed attempt (with why), confirmed password, sign-out and ended session, with the address and browser. The session's own transaction writes it. The email of a failed attempt is kept only as a keyed hash. The per-email sign-in limit now counts these rows, so it survives restarts and a second instance. The 180-day purge (API_AUTH_EVENTS_RETENTION) is built now rather than in phase 4, because the rows hold addresses. Administration's Security has three tabs: Sign-ins, every user's Signed-in devices (signing one out takes users.manage), and the Access review. Mark as reviewed is on the Audit log. On a phone, Roles & permissions and Settings moved under More.

Phase 3 is built (docs/specs/system-service.md). Every log line names its request, and a 500 answers with a reference the apps show in the user's language. 5xx answers, recovered panics and the apps' browser errors go on an error list, folded by kind and kept 30 days. Prometheus /metrics is on an internal listener. A 24-hour request window is kept in memory. Administration now opens on the Overview, which shows what needs attention and then figures, each area by permission. System has Status, Errors, and Backups as a tab. Found while building it: muxstack's Timeout runs handlers on their own goroutine, so a handler's panic would have stopped the API. It is now recovered inside Timeout.

Phase 4 is built (docs/specs/audit-service.md, ADR 0003). Each UTC day of the Audit log is sealed an hour after it ends, chained to the day before. Verify recomputes every seal hourly and on demand, and a mismatch is a critical item on the Overview. Audit events are purged after API_AUDIT_RETENTION (10 years), only whole sealed days, through an owner's function, and each purge is recorded. Export (audit.export) downloads CSV or JSON lines of a year at most, and each export is itself on the log. The API connects as ppe_app, which cannot change, delete or truncate the trails, and a TRUNCATE guard protects them. Found while building it: restores drop grants, so the role's grants are applied on every migrate.

Phase 5 is built (docs/specs/usage-service.md). Administration's Usage screen (usage.read) shows active people per day by app and role, sign-ins and failures, changes per area per week with the most active people, devices and languages, the confirmation-link funnel (sent → opened → confirmed, with what is waiting, expired or replaced), and the data's quality over 90 days. No page is tracked: activity is one row per person, app and day, written by the API. An employee's first opening of a link is now recorded on the order. The charts moved into @ppe/ui, which the Dashboards share.

All six phases are in production (609a0da). What is left, and what to do next, is in section 08.

Verdict

  • The audit trail is sound, but narrow and nobody can read it. Each row is written in the same transaction as its change, and the database rejects updates and deletes. Only 15 event types are recorded, and the only readers are an item's price history and the Manager Dashboard.
  • There is no security trail. Failed sign-ins are counted in memory and forgotten on restart; session rows are deleted 30 days after they end.
  • Monitoring is a log stream and a /health that never fails. No metrics, request IDs, error list, uptime check or alerts. Backups are the one thing watched properly.
  • Recommendation: grow Administration from 4 screens to 7 in five phases. Everything stays first-party, in this API, database and origin, which fits the 2 GB droplet, the CSP and GDPR. Log rotation and an external uptime check come first.

Gaps

high

User accounts are not audited: create, name/email edits, activation, password change and reset, delete. Only role changes leave a trace.

high

No security history. Sign-ins, failed sign-ins, sign-outs and stolen-cookie detection (end_reason = reused) are not kept; the limiter counts in memory.

high

The append-only rule has holes. TRUNCATE is not blocked (row triggers do not fire), TRUNCATE users CASCADE empties the table, and the API connects as the owner, so it could drop the trigger.

medium

Item sets, employee name/code/notes and catalogue name/details are not audited, so "who renamed this?" has no answer.

medium

The data sync writes tables directly as the sync user (migration 0011) and bypasses every service, so no events are written.

medium

No request context (request ID, session, source) and only an entity index: searching by time, person or event type scans the table.

medium

No seal, no retention. Tampering could not be detected; payloads hold personal data (confirmed_name, sizes) kept forever.

3.3 Request context on events

A. Typed columns

Recommended

request_id, session_id, source with a CHECK on staff | admin | public_link | sync | system.

  • Typed, indexable, enforced
  • One migration per new field

B. One context JSONB

Request ID, session, source, IP and user agent together.

  • Flexible
  • Unchecked
  • Invites personal data onto rows kept for years

IP and user agent stay on the session and the security event, which are kept for a short time. An administrator reaches them through session_id while those rows exist.

3.5 Integrity: making the trail tamper-evident

Step 1 · least privilege, needed by every option

Migrations run as the owner. The API connects as a new role ppe_app with only INSERT, SELECT on audit_events, audit_seals and auth_events; no UPDATE, DELETE, TRUNCATE or ALTER. This is the first piece of ADR 0001's per-schema roles. Tests keep truncating as the owner. A BEFORE TRUNCATE trigger adds defence in depth.

A. Hash chain per row

Each row stores sha256(prev_hash ‖ row), under an advisory lock.

  • Detects any change at once
  • Serialises every audited transaction
  • Commit order ≠ insert order

B. Daily seals

Recommended

After each day (+1 h grace) a job hashes the day's rows into audit_seals(day, rows, hash, prev_hash); seals chain. Verify recomputes them.

  • No lock on the write path
  • One row a day; old backups are witnesses
  • Today's rows open until sealed

C. Seals anchored outside

Later

B, plus each seal written to the backup bucket with object lock, or emailed.

  • Survives a full database compromise
  • Needs the outbox or bucket credentials in the API

3.6 Retention, export and GDPR

DataRetentionWhy
Business audit events10 years, purged by yearOrders and receipts are accounting records; Lithuanian accounting documents are commonly kept 10 years. Confirm with the accountant.
Security events180 daysLong enough for an incident; IPs are personal data
Ended sessions30 days (unchanged)
Error events30 days
  • Retention is configuration, not a screen (API_AUDIT_RETENTION, API_AUTH_EVENTS_RETENTION, read in loadConfig, checked in validate). A retention control in the UI would let one compromised admin account erase history. System shows the values.
  • Purge and seal jobs run in the API on a ticker under an advisory lock until ADR 0001's worker exists. The purge is the only deleter, through a SECURITY DEFINER function that refuses rows inside the retention, and it records audit.purged.
  • Personal data: new events carry IDs and field names, and values only where the value is the business fact (a price, a size, a status). Never passwords, notes text or ID numbers.
  • Export (audit.export): CSV or JSONL of the current filter, streamed, at most a year at a time, and recorded as audit.exported.

5.2 Tier 1: in the app

  • Request IDs. Middleware reads or creates X-Request-ID, adds it to every log line and response. Errors gain "reference", shown as "Reference 9f2c…" so a person can quote it. Audit events store it.
  • Error list. error_events holds 5xx responses, recovered panics and client errors (POST /api/v1/client-errors, same origin, rate-limited), folded by fingerprint per hour, kept 30 days. This is Sentry's useful core, with no third party.
  • Metrics. Prometheus /metrics on an internal listener (API_METRICS_ADDR) that Caddy never proxies. It covers routes, latency, status, pgxpool, runtime, sign-in failures, rate-limit hits, refresh reuse and audit writes.
  • Live figures. A rolling 24-hour window in memory (5-minute buckets) feeds the System screen; it resets on restart.

Follow-ups, done 7 Oct

The API connects as ppe_app: the password was generated on the droplet and never shown.

Backups go off the server: they are encrypted with age and saved to the Spaces bucket ppe-next2-backups (fra1). The private key is kept off the server.

Outages and the droplet are watched: an Uptime check of /ready, and CPU, memory and disk alerts in DigitalOcean Insights, with do-agent on the droplet.

A restore works (f15dbf1): make prod-drill restores the encrypted backup into a throwaway database. The grants come back, Verify passes and every table's count matches.

The Help guide covers Administration (1838e78, 484a7cb): the Overview, Audit log, Security, System and Usage, in three languages and on three devices.

The seals are anchored off-site (e78349d): each gets a trusted timestamp (RFC 3161) from DigiCert. All 162 are stamped, and one was checked with openssl ts -verify.

  4. An auditor role, or the Audit log for managers: a role holding audit.read, with no code needed (question 4).
  5. For a second API instance: move the per-address limit to Postgres, and add Grafana Cloud (EU) with Alloy on /metrics.
