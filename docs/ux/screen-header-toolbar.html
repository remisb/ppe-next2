One header for every screen

A page header that stays at the top while the screen scrolls, a toolbar with one order of controls, an optional menu button, and a screen-level ⋯ that also takes what does not fit on a phone. 2 · What sticks

Four options, each scrolled half way down SIM Cards

All four keep the bottom bar, the detail pane and Create Order's summary as they are.

Why B

  • Every screen keeps its title and actions at any scroll position, for no more height than the bar it replaces.
  • One row that never changes height: nothing jumps when it sticks, and nothing flickers on and off at the edge.
  • The filter bar is one step away: Filters on a phone, / on a desktop.
  • The same row serves records, so a pane and a page read like a screen.

What B costs

  • The emblem is covered once the user scrolls 56px (open question 1).
  • Filter tabs and their counts scroll away; a filtered list does not say so while deep in it.
  • A sticky element can hide what has focus: scroll-padding-top is required, not optional.
  • Twenty headers move to one component, so every list screen is touched once.

3 · The page header

One row, stuck to the top

The full toolbar, as the Audit log would have it on a desktop with every slot used. Most screens use two or three slots.

Audit log1i2
Filters (2)3 Refresh4 Export5 Area: All6 Primary7 8
Times are in Europe/Vilnius. — the subtitle line, when there is one, scrolls away

The parts

  1. Title, the h1. Truncates with an ellipsis before any control wraps.
  2. ⓘ, the description (InfoTip), as now. Never a line under the title.
  3. Filters, phone only, with the count of filters set.
  4. Refresh, on screens of live figures. Icon on a phone.
  5. Secondary, outline. Two on a desktop, one on a tablet, none on a phone.
  6. Menu button, optional: one kind of choice, label and chevron. (Illustration only; the Audit log has none.)
  7. Primary, filled, at most one, next to ⋯ as in every record header.
  8. ⋯ More actions: overflow, then rare actions, then what asks first. Always last.

How it sticks

  • position: sticky; top: 0 in main, the screen's background; at rest no rule, stuck a rule and a soft shadow. The height never changes.
  • Stuck is a data-stuck set by an IntersectionObserver on a 1px mark above the header (this page does the same).
  • Phone: the emblem bar stays z-30; the header is z-40 and opaque, so it covers the emblem bar after 56px.
  • Tablet, desktop: the header spans the list's column; an open pane keeps its own top, aligned with the header's.
  • --page-header (56px, 64px from md) feeds column heads, Create Order's summary and the root's scroll-padding-top, so focus, / and Help's #links never land under it.
  • Below 30rem of window height (a phone on its side, a zoomed laptop) it does not stick. In print it is static and the toolbar hidden.
  • Not on the confirmation page, hand-over mode, documents or sign-in.
4 · Toolbar and ⋯

What does not fit goes into ⋯, by width

Each control says from which width it is a button (showFrom); below it, it is an item in ⋯ in the toolbar's order. Both are rendered and CSS shows one; the menu's items mount only while it is open, so a screen reader never meets both. Drag the box's corner to change its width, and switch the language.

Slot defaults

  • Filters: below md only.
  • Refresh: always; icon only below md.
  • Secondary: a button from md; in ⋯ below.
  • Menu button: a button from sm.
  • Primary: always, with its words. Where the header is too narrow for title and words (LT and RU at 375px are the test), only the icon, with its name and a tooltip.
  • ⋯: hidden at widths where it would be empty.

A screen's ⋯ holds, in order

  1. The overflow, in the toolbar's order.
  2. A separator, then rare actions that are never buttons: set-up tasks, monthly exports (Pictures).
  3. A separator, then what asks first or empties work, with "…" (Clear order…).

Never empty; never a lone item that is always there (that is a button). Named "More actions for ⟨screen⟩". No view settings that Account and ⌘K hold.

Why not measure

  • A ResizeObserver that moves buttons as text changes re-renders on every resize and language switch, and differs between a test run and a real phone.
  • Breakpoints are what web/AGENTS.md already uses; e2e checks them at fixed widths.
  • Prints and the first paint are right without JavaScript.

5 · Lists

The filter bar stays put; column headings stay in view

The filter bar keeps its place under the header and does not stick. Every list puts its parts in one order.

One order on every list

  1. Filter tabs with their counts, on their own row. Employees moves its tabs above its search.
  2. Search (/ reaches it), then the filters, then Sort ▾ at the end, then Clear filters when any is set.

On a phone, everything after the tabs and the search stays behind Filters. A tap on Filters in a stuck header scrolls the filter bar back under the header, opens it and focuses its first field. / on a desktop scrolls the search into view the same way.

Sort ▾ instead of the Sort by row

One menu button that says the order in words ("Name, A–Z", "Date, newest first"). Its menu lists the columns as radio items, then a separator, then the two directions in words. While the table is wide, its sortable headings stay the way to sort and the button is hidden, as SortControl is today.

Column headings

On a desktop, a wide Table with stickyHead keeps its <thead> at top: var(--page-header). Where it sticks, Table swaps its wrapper's overflow-x-auto for overflow-x-clip, because a scroll container would hold the heading instead of the window; these tables already stack rather than scroll sideways. Group rows (Orders' months) do not stick: two layers of sticky rows read as a second header.

Why the filter bar does not stick

Lists are paged at 20 (Orders) or hold a few dozen rows (Employees, Item Catalogue, the registers), so the filter bar is rarely more than a screen away. On a phone, header, tabs and search together would take about 164px, plus the 52px bottom bar: under 60% of the screen left for the list.

6 · Records

A record's first row sticks too

In the detail pane, inside its own scroll; on a phone or tablet, where the record is the screen, as the page header. Details, badges, facts and sections scroll under it. Below lg the back link becomes an icon in that row; beside the list, ✕ keeps the corner.

Rules for the record row

  • Order: back (below lg) · title · main action · ⋯ · ✕ (beside a list).
  • The main action stays in the row at every width. On a phone: icon and a short label where the dictionary has one (Create link, Kurti nuorodą…), else the icon with the full name.
  • Other actions stay outline buttons under the facts, above long content, as the guidelines say.
  • The row's ⋯ and the list row's ⋯ hold the same items in the same order.

Short labels needed

About eight, each in EN, LT and RU. Only the main actions that are longer than about 14 characters: Create confirmation link → Create link, Add New Employee (none, the icon), Mark as Not Returned (it is not a main action). New order, Edit, Give SIM, Return, View Order fit as they are.

Flow 4 · Keyboard and screen reader

Skip to content→ i→ Refresh→ Export→ → Search the log→ …
  1. Tab reaches the title's ⓘ, then each toolbar control in the order shown, then the filter bar. The toolbar is a labelled group, not role="toolbar": that role promises arrow-key movement inside it, and a header of three controls is quicker with Tab.
  2. / focuses the search; the root's scroll-padding-top: var(--page-header) scrolls it to just below the stuck header, so it is never hidden (WCAG 2.2, 2.4.11 Focus Not Obscured).
  3. On ⋯, Enter opens; the arrows move; typing a letter jumps; Escape closes and puts focus back on ⋯.
  4. Sticking is never announced. Nothing changed but the scroll position.
  5. Every icon-only control has a name and a tooltip: "Refresh", "Back to Orders", "More actions for Audit log".

Flow 5 · Switch dashboards

  1. An administrator who is also a manager opens the Dashboard. The toolbar shows Refresh and Dashboards ▾.
  2. Choose Dashboards: Administrator (ticked), Manager, Employee — only those the user's roles open.
  3. Choose Manager: the Manager Dashboard opens, its menu with Manager ticked. Back returns to the Dashboard.

A user with one dashboard has no menu button.

Flow 6 · Sort a stacked list

  1. Employees on a phone. In the filter bar, after the search: Sort ▾ reads "Name, A–Z".
  2. Choose it: Name, Code, Height, Clothing, Shoes as radio items; a separator; A–Z, Z–A.
  3. Choose Z–A: the menu closes, the list re-sorts, the button reads "Name, Z–A". On a wide table the button is hidden and the column heads sort, as now.

A sketch of the API

<PageHeader title={t.assets.simCards} description={…}>
  <Toolbar more={t.common.moreActions(t.assets.simCards)}>
    <ToolbarFilters count={extra} open={showFilters} onToggle={…} controls="asset-filters" />
    <ToolbarAction icon={FileText} label={t.assets.previewPdf} onSelect={previewPdf} showFrom="md" />
    <ToolbarAction primary icon={Plus} label={t.assets.addSimCard} onSelect={() => setEditing('new')} />
  </Toolbar>
</PageHeader>

Each ToolbarAction renders as a Button in the row and as a DropdownMenuItem inside ⋯ (a context says which); CSS shows one per width. Slot order is fixed by the component, not by the order a screen writes them in.

Open questions

  1. Brand on a phone: is the emblem at rest, covered after 56px, enough? Or the screen's title in that bar from the start, the emblem only in More?
  2. Create Order on a phone's Orders: hide it, since the bottom bar's raised New order is the same action?
  3. Two primaries with a pane open: keep both filled, or the screen's outline while a pane is open?
  4. Clear order into ⋯ as Clear order…: used often enough to stay a button?
  5. Option C for the Audit log, later, if people filter it while deep in the list?
