Proposal

One front door for the company's apps

App Launcher is a page of big buttons, like a till or the Shortcuts app, that shows each person only the apps their roles use. It also lets us put proof-of-concept apps, trials and new versions in front of chosen testers without new DNS records, new addresses or Caddy changes.

4apps today: Workwear, Administration, Scan SIMs (trial), PPE Crew (separate system)
~12places edited by hand to add Scan SIMs (Caddy, CSP, Dockerfile, Vite, e2e, routing, app identity)
0config changes per app after phase 3: register it, CI publishes it
3hosting tiers, by how much we trust the code

The problem

  • Too many doors. People learn an address per app, and the staff app's sidebar already holds more than most roles use.
  • Trials are expensive. Scan SIMs needed its own Caddy block, its own CSP line, Dockerfile and e2e changes, and still reports to the API as workwear because adding an app name touches two database CHECKs.
  • No versions. Everyone gets the same build. There is no way to let three testers try the next Scan SIMs while the rest keep the current one, or to compare two designs.
  • PPE Crew lives elsewhere, at crew.167.71.68.195.sslip.io, with a second sign-in. Nobody finds it without the link.

The recommendation in short

  • A fourth app, App Launcher, at /apps/ on the staff app's origin, sharing its sign-in.
  • A registry of apps, their versions and channels (Stable, Beta, Preview), and who sees each. Static at first, then in the API with a Manage apps screen.
  • Tiers: apps built and reviewed here run at /apps/<slug>/ with your sign-in. Outside code runs on a sandbox domain and never sees it. Separate systems such as PPE Crew are linked.
  • One Caddy rule sends /apps/* to the API, which serves each published build with the security policy it declared. New apps and versions need no config.
  • People with one app skip the launcher. Testers turn on Show apps in testing.
  • No app loses a row to the launcher: the way back is an Apps entry in each app's own menu, and a version shows only when someone is off Stable.
Already decided: tiered hosting (built here shares the origin; outside POCs go to a sandbox), deliverables in the repo and as shared pages, and a clickable prototype to test with people. The open decisions are on the Decisions tab, each with a recommendation.

Why this lowers the load on people

  • Fewer choices, faster picks. The time to choose grows with the number of options (Hick's law), so each role sees only its apps.
  • Recognise, don't recall. Icon, colour and name together; no addresses to remember.
  • Places that stay put. Tiles keep their position, as on a till, so hands learn them. Search and pins are extras, never the only way.
  • Detail on request. Versions, details and feedback sit behind ⋯, a long press or a right-click.
  • No launcher when it adds nothing. Someone with one app goes straight in.

What it must not do

  • Hiding is not security. A tile's audience decides what people see. What they can do stays with the API's permissions, as today.
  • No second shell. ADR 0001 keeps one staff app of modules. The launcher is a front door, not a frame around apps. Each app keeps its own header. The way back is an Apps entry in the app's own menu, never an extra row.
  • No iframes. Apps open as pages. The CSP forbids framing other sites, and frames would break sign-in, the camera and deep links.

How it would work

One origin for what we trust, a sandbox for what we don't

The deciding fact: the sign-in cookie ppe_refresh (path /api/v1/auth, cmd/api/auth-cookie.go) lets any page on workwear.gavort.nl get a token with all of the person's permissions. So whatever runs on that origin is trusted as much as Workwear itself.

Serving a version without config

  1. CI builds the app in web/apps/<slug> with relative asset paths and uploads dist/ with a small manifest (slug, version, capabilities, minimum API version): make app-publish SLUG=… VERSION=… DIR=….
  2. The API stores it in the files store under apps/<slug>/<version>/ and records the version (an audit event).
  3. A request for /apps/sim-scan/beta/… resolves the channel, serves that version's index.html (no-cache) with asset links rewritten to /apps/sim-scan/@<version>/assets/… (cached for a year) and a <meta name="ppe-mount"> the router reads. The CSP's base-uri 'none' rules out a <base> tag.
  4. Moving a channel changes only what the next load gets. Open tabs keep loading their own version's files.

Security policy per version

Today Caddy has two CSP lines: the staff policy and Scan SIMs' (adds 'wasm-unsafe-eval', worker-src 'self' and the camera). Under /apps/ the API builds the header from a closed list of capabilities a manifest may ask for:

CapabilityAdds
wasmscript-src 'wasm-unsafe-eval'
workersworker-src 'self'
cameraPermissions-Policy: camera=(self)

Anything else needs a code change and review. The inline theme script stays allowed by its one hash, as in every app now.

One API, many front-ends

Versions are front-end builds only. Every version talks to the same API and database, so:

  • API changes stay additive, and ship before the front-end that needs them.
  • A manifest names the oldest API it works with; the launcher hides a channel whose API is not deployed yet (/ready already reports the commit).
  • Requests carry X-PPE-App: <slug> and X-PPE-App-Version, so Usage and System's error list can be read per app and version. Today AppName in api-client/src/client.ts allows only workwear | admin.

Why the sandbox needs its own domain

  • The refresh cookie is host-only, so <slug>.apps.gavort.nl never receives it. But that address is same-site with workwear.gavort.nl: SameSite=Strict does not stop its requests, and a page there could set cookies for all of gavort.nl.
  • The cookie routes' Origin check (sameOrigin) refuses such requests today, so *.apps.gavort.nl would be safe enough. A separate registrable domain (the way Google serves user content from its own domain) removes the question for about €10 a year.
  • For a POC on day one, <name>.<ip>.sslip.io works with no DNS at all, as PPE Crew does now. It is a shared public domain, so no HSTS.

The way back to the launcher

The launcher adds no row to any app. Every app has an Apps entry in its own menu, and ⌘K finds apps too. One quick way back may be added on top; try each with Way back in the prototype's bar (flow 8).

OptionScreen spaceNotes
A. In the app's own menu (always)NoneSidebar or rail foot on tablet and desktop, the More panel on a phone: where Workwear's Administration link is today.
B. ⌘K “Go to app…” (always)NoneThe staff app's ⌘K search lists apps and shortcuts too.
C. Icon in the app's top barNoneA 44px grid icon beside the avatar. One tap, but crowds a phone's header.
D. Floating buttonCovers a corner; hides while scrolling downSuits the counter tablet. Can hide content and actions.
E. A bar of its ownOne row, alwaysOnly for small apps with no header of their own, such as some POCs.

Which version am I on?

  • Stable: nothing shows.
  • Beta, Preview or a variant: a 3px stripe in the channel's colour under the address bar, and a dot on Apps (on More on a phone).
  • The exact version is under the menu's Apps entry and in the tile's About.

Who chooses

  1. The app, in the registry: which quick way back it allows, if any. Full-screen modes (hand-over mode, stand-up, the public confirmation page) never show one.
  2. The roles: someone with one app sees no way back (D10).
  3. The person, on Account: “Show the Apps button in the header” (off by default) and “Show which version I'm on” (default: only when not Stable).
  4. The device: a counter tablet in kiosk mode hides it.
UX flows

Seven flows to try in the prototype, plus its flow 8 for the way back

1 · Sign in, land where you work

  1. Sign in once on any app
  2. One app? It opens straight away
  3. More? The launcher at /apps/
  4. Last used and pinned apps on top

Staff with the employee role use only Workwear, so nothing changes for them.

2 · Find and open

  1. Tap a tile, or type two letters
  2. The app or screen opens as a page
  3. Apps in its own menu comes back
  4. Pin what you use daily

Shortcuts reach a screen in one tap: Create Order, SIM Cards.

3 · Try a beta, then go back

  1. Tester turns on Show apps in testing
  2. ⋯ on Scan SIMs, choose Beta
  3. Opens /apps/sim-scan/beta/
  4. Switch back to Stable any time
  5. Feedback goes out with the version

4 · Promote, then roll back

  1. Manage apps → Scan SIMs
  2. Make stable on the beta's version
  3. Everyone's next load gets it
  4. Roll back moves the pointer back

No rebuild, no deploy; both moves are audit events.

5 · Add a POC: no DNS, no Caddy

  1. Create web/apps/<slug> from the template
  2. Register app: name, tier, group
  3. CI runs make app-publish → Preview
  4. Testers see it in Labs

6 · An outside POC

  1. Register with tier Sandbox
  2. Its address: <slug>.<sandbox domain>
  3. First visit gets a certificate
  4. It runs without anyone's sign-in

7 · Open a linked system

  1. Tap PPE Crew (↗)
  2. A new tab at its own address
  3. Its own sign-in, same email and password
  4. Later: one sign-in, or merged in

Retire an app

  1. Stage → Retired
  2. Tile disappears; old address shows where it went
  3. Versions kept 90 days, then deleted

When Scan SIMs merges into SIM Cards (ADR 0005), its tile becomes a shortcut.

Roadmap

Small steps, each usable on its own

Each phase can stop there and still be worth it. Sizes are rough: S a few days, M one to two weeks, L more.

0now

Decide and test the idea

This guide, the prototype and ADR 0006 (proposed). Run the test plan with 5 to 8 people. Nothing changes in the product.

1S

Launcher with a static list

web/apps/launcher at /apps/, sharing @ppe/app-shell's sign-in. The list lives in code (@ppe/routing), with audience by permission. An Apps entry in every app's own menu (More on a phone, the sidebar elsewhere) and in ⌘K. Tiles for Workwear, its shortcuts, Administration, Scan SIMs and PPE Crew. Adding the launcher itself costs what Scan SIMs cost, once.

2M

Registry in the API

internal/domain/launcher (apps, channels, audiences, pins, feedback), GET /api/v1/launcher filtered on the server, Manage apps on Administration with a new permission apps.manage, a Testers built-in role, app identity from the slug (one migration widens the two CHECKs).

3M–L

Versions and hosting at /apps/

One Caddy rule; the API serves builds from the files store with the CSP from capabilities; api -publish-app and a CI job; channels and @version addresses. Scan SIMs moves first, and its Caddy block and CSP line go.

4M

Sandbox domain

A wildcard record on a separate domain, Caddy on-demand TLS asking the registry. Later, if a POC needs real data: a short-lived token limited to the routes its manifest names.

5S–M

Trials view

On Manage apps: opens per version and day (from Usage), errors per version (System), feedback, and a Promote / Retire decision with its reasons, as the evidence for "merge it or drop it".
