App Launcher Handbook

The front door of the company's apps, at /apps/. Each person sees only what their roles open, signs in once, and an administrator adds an app without touching DNS, servers or the web server.

For staff, administrators and developersDecisions: ADR 0006Rules and routes: docs/specs/app-launcher.mdTerms: glossary §13
Staff

Less to remember

One address and one sign-in. Only their own apps, by permission, with pins and recent apps. Someone with one app never sees the launcher.

Administrators

A new tile in minutes

Register app on Manage apps. Trials stay with Testers; Make Stable on an older version rolls back at once; every change is audited.

Developers

No infrastructure per app

One registry, one route and one Caddy rule serve every published app. A build is a folder plus a small JSON file.

For administrators

Register a tile

Names in EN, LT and RU; a slug set once; App or Shortcut; group, stage, picture, colour (white text must pass 4.5:1); On this site with a path, or Another site with an https address.

Who sees it

Everyone signed in, or holders of any ticked permission. Seeing a tile grants nothing: the API still checks every action. Retired hides a tile and keeps its history; tiles are never deleted.

Order, feedback, history

Move earlier and Move later; Feedback, newest first; Changes lists every edit and who made it.

Ship a build to everyone

  1. Deploy: the build lands on Preview.
  2. Try it at /apps/sim-scan/preview/.
  3. ··· beside the version → Make Stable. A note says while Preview is ahead of Stable.
  4. For an app no one tries first, turn on Stable follows deploys: every deploy then reaches everyone.

Let a few people try it first

  1. Make Beta on the new version.
  2. Give those people the Testers role, or name a permission on the channel.
  3. They choose Beta under Versions in the launcher.

Roll back

  1. ··· beside the previous version → Make Stable.
  2. Done at once; nothing is rebuilt. The move is in Changes and the Audit log.

Compare two designs

  1. Publish both builds.
  2. Add variant for the second, with a label and an audience.
  3. Compare the feedback each one gets.
Technical

How it works

Registry

internal/domain/launcher, migrations 0042–0045: tiles, pins, feedback, versions, channels, each user's channel choice, and who opened which version (Trials). Every change is an audit event (app.*). Default tiles live in defaults.go; code owns each until an administrator changes it: untouched ones follow the code at start-up, audited, and edited ones are never overwritten.

API

GET /api/v1/launcher (tiles, pins, channels, choices), PUT …/pins, POST …/feedback, PUT …/choices/{slug}; Manage apps under /api/v1/apps…; the public page route GET /apps/{slug}/{rest...}.

Addresses

/apps/<slug>/ is Stable, /<channel>/ a channel, /@<version>/ one exact build; anything after is the app's own screen. Meta tags: ppe-mount, ppe-files, ppe-version, ppe-channel. Each version's page is rewritten once and sent with an ETag, so a reload while no channel moved is a 304.

Publishing

api -publish-app reads a tar of dist/ on standard input (up to 5000 files and 300 MB, no links) and never replaces a version, but writes a recorded version's files again when they are missing, so builds need no backup. make prod-up publishes to Preview, then prunes what no channel opens beyond the newest five and folders no version names, and publishes nothing from a checkout with local changes; make prod-publish APP= REF= CHANNEL= builds any git ref on the droplet.

For developers

Designing a new app

Choose the simplest home that works. The default is a screen in the staff app: ADR 0001 keeps one staff app of modules, and a separate app is justified by another audience, device or trust level, not by another team or feature.

A new screen for the same peopleA screen in the staff app or Administration, plus a shortcut tile if it deserves oneDefault
Quick access to an existing screenRegister a shortcut on Manage appsNo code
A system that already exists elsewhereRegister a linked tile (↗); it keeps its own sign-inNo code
Another audience, device or trust level, or a trial to roll back on its ownA published app in web/apps/<slug>A day to set up
Code not reviewed hereNot on this site: a linked site now, the sandbox domain later (phase 4)Off-site

Checklist for a published app

  1. make new-app SLUG=<slug> NAME='<name>' NAME_LT='…' NAME_RU='…' starts web/apps/<slug>/ from web/templates/published-app: ApiProvider app="<slug>", SignedIn and AppFrame, a first screen, words in EN, LT and RU, csp.test.ts and the Tailwind test, vite.config.ts and public/ppe-app.json with the next free devPort. The manifest is what makes it a published app: the build, the deploy, the dev proxy and e2e find it there. It also adds the tile to defaults.go in POC (Testers only), since a deploy and e2e publish only a registered app; set its group, icon and colour there. It runs pnpm install for you.
  2. Add a capability to the manifest only when needed: each one widens the policy (then test that profile's policy, as Scan SIMs' csp.test.ts does).
  3. Use basePath for the router and filesBase for your own static files, never import.meta.env.BASE_URL.
  4. Add screens as tabs of AppFrame (the template's router has one); let each screen's PageHeader be the only sticky header, as AppFrame's bar scrolls away.
  5. Tests: the app's unit tests and an e2e step (Vite mode uses its dev server; Caddy mode publishes it).
  6. Ship: deploy → Preview (and Stable, the first time) → Testers try it → move its stage on Manage apps when it is for everyone.

Rules that keep it simple

  • One sign-in, one origin, one API. No second backend for an app; API changes stay additive.
  • Access is decided by permissions in the API; a tile's audience only hides tiles.
  • A version never changes; to change it, publish another.
  • No app-specific Caddy, DNS or policy edits. If you need one, it is a new profile and a review.
  • Words in all three languages from day one; Help covers the app like any other screen.
Review

Critique

Reviewed again on 5 November 2026, after improvements 1–9, through four lenses: safety, simplicity, efficiency and maintainability. Each finding was checked against the code and names where it is.

What works well (keep it)

  • The trust boundary is explicit: only code reviewed here runs on the site, with the user's sign-in; anything else is a linked site.
  • Publishing is careful: untar refuses links, devices, .. and absolute names, caps size and file count, extracts beside the destination and renames it into place; a version is never replaced.
  • Rolling back moves a pointer: pruning and moving a channel lock the same app row, a foreign key backs it, and choices are kept by channel name, so pruning never strands one.
  • Policies come from a closed list: files live under their profile, Caddy serves only the known ones, and tests keep the Go and Caddy copies (and the icon lists) equal.
  • Cheap where it is used most: one GET /api/v1/launcher per page, shared by the frame, the stripe and the staff app's sign-in.
  • A new app is one command, and CI builds the template, so it cannot rot unnoticed.

Safety

S1

A lost published volume is never rebuilt High

The docs say builds are rebuilt from git rather than backed up, but api -publish-app writes files only for a version it has no row for. After a restore onto a new droplet, or a lost volume, the database names versions whose folders are gone: /apps/sim-scan/ answers 500, and prod-up or prod-publish reports "already published" and writes nothing.

Fixed (improvement 10): publishing decides by the folder, so the same commit published again puts missing files back, and -prune-apps removes what no version names.

cmd/api/publish-app.go:61-81

S2

Signing in as someone else on the same page shows the previous user's launcher Medium

useLauncher keeps the last list until the new user's arrives, the launcher copies pins and choices into state once, and signing out does not reload the page. On a shared tablet, B briefly sees A's tiles and pins; pinning then saves A's pins to B's account. Every app's Apps entry and channel stripe read the same stale list.

Fixed (improvement 11): the list is given only to the user it was loaded for, and the launcher starts afresh for each user; a test switches users.

@ppe/launcher load.ts:57-68; apps/launcher/src/app.tsx:80,84

S3

A channel's audience decides who sees it, not who can open it, and the check fails open Medium

The page route is public by design (the data stays behind the API's permissions), so the stripe's redirect is the only gate, and it lets anyone stay while the list loads or fails. A Preview or variant build, or any kept @<version>, opens for anyone with the link, signed out included. Nothing in the spec says so.

Fixed (improvement 13): the spec says an audience is what people see, not what they may open; the stripe waits while the list loads and sends the user to Stable once it fails.

channel-stripe.tsx:27; published-app-routes.go:41,54

S4

Gaps in the audit trail and half-done publishes Low

A new variant's audience is not recorded (only app.channel_moved). Publishing to an unknown variant records the version before refusing. Two publishes of one version at once can delete the first one's files. The prod-up publish pipe has no pipefail, so a cut-off tar might be published as complete (suspected, not shown).

Fixed (improvement 14): a new variant's label and audience are recorded; the variant is checked before anything is written; the publish pipes run with pipefail. Two publishes at once keep the first's complete folder (improvement 10).

service_versions.go:93,107,201; publish-app.go:71; Makefile prod-up

S5

Production runs a Caddy no test ran Low

The web image is FROM caddy:2-alpine, while CI and make e2e-caddy pin CADDY_VERSION and its checksum. A rebuild can pick up a Caddy the policies and redirects were never tested on.

Fixed (improvement 12): the image builds on caddy:${CADDY_VERSION}-alpine, which a test keeps equal to CI's.

web/Dockerfile:33

S6

Failures the user never sees Low

Saving pins or a channel choice reverts silently when it fails. Back to Stable swallows a failed save, and the Stable address then sends the user straight back to the channel they chose. Device pins from phase 1 are deleted before the API has saved them.

Fixed (improvements 13 and 15): failed saves are shown and undone; Back to Stable goes to /stable/ when the save fails; device pins are forgotten only once saved. Showing the error found two pin saves at once failing on each other (“app slug already in use”); the API now takes them in turn.

apps/launcher/src/app.tsx:98-118; channel-stripe.tsx:43-47

Simplicity

P1

A lot of machinery for one app Medium

About 1,900 lines (versions, channels, the page route, publishing and pruning, the stripe, Releases, Trials, three migrations) serve Scan SIMs alone. Variants with audiences, per-user choices, Stable follows deploys and Trials have not been needed by a second app yet. Capabilities are decorative: declaring any one gives the whole device profile.

internal/domain/launcher/versions.go:31-41

P2

Fixed ports are written in six places Medium

The staff app's, Administration's and the launcher's ports are listed in new-app.ts, e2e/env.ts, two Vite configs, .claude/launch.json and CLAUDE.md; make new-app adds nothing to launch.json.

new-app.ts:55; e2e/env.ts:14-18

P3

Repeated code Low

The launcher repeats SignedIn; Administration repeats the launcher's stage and rating words in three languages; three Playwright server entries are near copies; the template's Vite config is Scan SIMs' minus two plugins.

Fixed (improvement 19): the launcher uses SignedIn; Administration reads the launcher's stage and rating words; one viteServer helper starts the e2e servers. The template's Vite config stays a copy, kept by pnpm check:new-app.

apps/launcher/src/app.tsx:48-73; e2e/playwright.config.ts:60-87

Efficiency

E1

Every page load redoes the same work Low

Opening a published app runs three queries (one loads every app's channels and filters in Go), reads index.html from disk and rewrites it, and is sent no-cache without an ETag, so it is never a 304. A version's page never changes.

Fixed (improvement 18): the rewritten page is kept per version and sent with an ETag, so a reload is a 304; channels are read for one app.

service_versions.go:258-270,439; published-app-routes.go:72-96

E2

One dev and e2e server per published app Low

Every published app starts its own Vite server in development and e2e, whether a test uses it or not; the cost grows with each app.

e2e/playwright.config.ts:70-77

Maintainability

M1

Rules copied by hand with no test Medium

The slug rule and reserved slugs are in Go, in new-app.ts and in Administration (for slugs and variant names), and must also match Caddy's /apps/ paths. The profile's policy is an if/else, so a third profile would silently get the staff policy.

Fixed (improvement 16): the slug rule lives in app-slugs.ts, which a Go test reads; profiles map to policies, and tests check every profile and reserved slug against Caddy.

app.go:120,123; apps/admin/src/lib/apps.ts:90,137; published-app-routes.go:89-94

M2

A variant can take a screen's address Low

The first path segment is a channel when one has that name, so a variant called find would take over Scan SIMs' /find for everyone.

service_versions.go:478-481

M3

Leftovers are never cleaned Low

A killed publish leaves .incoming/ behind, and folders no version names stay, and Caddy serves them.

publish-app.go; Caddyfile:60-65

M4

Risky paths without tests Low

untar is tested only with ../: not with links, absolute names, duplicates or its caps. Nothing tests publishing a recorded version whose files are gone, a page with no </head> (its meta tags are dropped silently), the stripe's redirects, or useLauncher when the user changes; S1, S2 and S6 would have shown there.

Fixed (improvement 17): untar is tested with links, devices, absolute and escaping names, duplicates and both caps; a page without </head> is refused when published and an error when served; the stripe's choices are pure functions with tests (mayStay, stablePath, chosenHref).

api_postgres_test.go:2082

M5

Small slips Low

X-PPE-App-Version is set twice on downloads; Scan SIMs' package.json still says /sim-scan; make new-app copies the template before checking its placeholders, so a bad template leaves a half-made folder.

Fixed (improvement 19): the header is set once; the description names /apps/sim-scan/; make new-app fills every file before writing any.

api-client/src/client.ts:176-177; new-app.ts:96-102
