Company Assets UX Review
SIM cards and equipment brief (v1.0, 2026-10-08) compared with PPE-next2 at commit 4fc207e
Verdict

The brief fits PPE-next2, but the core is new

The people, access, form printing, snapshots and audit trail are already there. What the app has never had is an individual item: something with its own number that one employee holds and later returns. That record needs a new Company Assets context in the same API. It also needs a file store for signed scans, which the app does not have yet.

Brief requirements by how much of the app they reuse

What carries over

  • Employees, the employee picker and the employee page. The brief forbids a second employee database, and none is needed.
  • Atomic changes: the repository locks the row (FOR UPDATE), runs the mutation and writes the audit events in one transaction. That already covers "one action updates everything" and "no partial assignment".
  • Frozen documents: immutable order_lines snapshots and the document hash. Reuse them so an assignment form never changes when a plan or value changes later.
  • A4 print, FormSheet, Table stack, Kpi tiles, ⌘K Search, RecordChanges, the organisation timezone and the server-computed durations.

What is missing

  • Units, return, location, stock: today an item on a Given order counts as given forever, and there are no inventory or serial numbers.
  • File upload and storage: there is none. The API accepts JSON up to 1 MB, and backups dump only Postgres.
  • Employment status: the brief says leaving never returns items, but employees only have a soft delete.
  • Company name and provider contacts: Settings holds only the supplier's WhatsApp group.
  • A "no Confirm windows" rule: paper confirmation uses window.confirm today, and the new flows must not.

Recommendation

Option A + B + C entry points · chosen 2026-10-09

Build Company Assets as a register first (Option A). The SIM Cards and Equipment & Furniture tabs share summary tiles that filter the list. Each row offers the one action that fits its state, and every action opens a short sheet over the list. Add a per-item page for the assignment timeline, documents and phone use (Option B). Start assignments from the employee page too, and accept SIM, phone and inventory numbers in ⌘K Search (Option C). This takes the fewest taps across the nine key actions (43 on desktop), keeps every gate the brief requires, and reuses the app's own components.

Rules model

Three things that change independently

The brief's main rule (§2) is that a card's connection status, its physical location and the person it is assigned to are separate facts. A blocked card is not a returned card. A card at an unknown location still has a last holder. The UI should show them as three separate things and never let one action change two of them by accident.

Data shape (proposal)

  • assets: kind (SIM / EQUIPMENT), category, inventory_no (unique), sim_no as text so leading zeros survive (unique), phone, provider, plan, non-return value and currency, connection status (SIM only), received date, comment, soft delete, and later written_off_at.
  • asset_assignments: asset, employee, given date, given by, created at, returned date and returned by, the not-returned mark with its comment and whereabouts, form snapshot JSON with document_hash, paper signed, and signed copy. A partial unique index allows one open assignment per asset, so the database itself stops a double give.
  • asset_number_counters: one counter per prefix (SIM, PC, PH, DRV, FUR, AST). A manual number is accepted if it is unique; a number is never reused.
  • Office stock, With Employees and Days Held are derived from open assignments and never stored, so nothing can drift apart.
